# 碎片同步深度分析 (Diff-Patch Sync Analysis)

> 基于 Simperium 源码 (`node_modules/simperium/`) 的完整逆向工程分析

---

## 一、Simperium 官方碎片同步架构详解

### 1.1 核心概念

```
┌─────────────────────────────────────────────────────────────┐
│                    Simperium 同步模型                         │
│                                                             │
│   Client A                 Server                Client B   │
│   ┌──────┐                ┌──────┐              ┌──────┐   │
│   │ Note │  ──diff──►     │ Note │   ──diff──►  │ Note │   │
│   │ v3   │  ◄──patch──    │ v3   │   ◄──patch── │ v3   │   │
│   └──────┘                └──────┘              └──────┘   │
│   ┌──────┐                                      ┌──────┐   │
│   │Ghost │  (上次同步时                          │Ghost │   │
│   │ v3   │   的数据快照)                         │ v3   │   │
│   └──────┘                                      └──────┘   │
│                                                             │
│   编辑后:                                                    │
│   diff(ghost_v3, current_data) = patch                      │
│   发送 patch 到服务器 (而不是完整数据)                         │
│   服务器 apply(ghost_v3, patch) = ghost_v4                   │
│   广播 patch 给其他客户端                                     │
└─────────────────────────────────────────────────────────────┘
```

### 1.2 五大核心模块

#### ① Ghost (影子副本) — `ghost/store.js`

Ghost 是每个笔记"上次同步成功时"的完整数据快照。

```javascript
// Ghost 数据结构
{
  key: "note-uuid-123",    // 笔记 ID
  version: 3,              // 当前同步版本号
  data: {                  // 完整的笔记 JSON
    content: "Hello World",
    tags: ["work"],
    modificationDate: 1713945600
  }
}
```

**工作原理：**
- 本地编辑 → `diff(ghost.data, edited_data)` → 生成最小补丁
- 收到远端补丁 → `apply(ghost.data, remote_patch)` → 更新 ghost
- Ghost 始终保持与服务器"最后一致"的状态

**官方实现：内存存储** (84行代码)
- `put(id, version, data)` → 存入 `this.index[id]`
- `get(id)` → 从 `this.index[id]` 读取
- `remove(id)` → 删除
- `getChangeVersion()` / `setChangeVersion(cv)` → 记录同步游标

#### ② JSONDiff (差异算法) — `jsondiff/jsondiff.js`

Simperium 的核心算法，支持多层嵌套的 JSON 差异计算。

**支持的操作类型：**
| 操作码 | 含义 | 示例 |
|--------|------|------|
| `+` | 添加字段 | `{o:"+", v:"new value"}` |
| `-` | 删除字段 | `{o:"-"}` |
| `r` | 替换整个值 | `{o:"r", v:42}` |
| `d` | 字符串 diff (diff-match-patch) | `{o:"d", v:"=5\t+inserted\t=10"}` |
| `O` | 对象递归 diff | `{o:"O", v:{nested_diffs}}` |
| `L` | 列表递归 diff | `{o:"L", v:{index_diffs}}` |
| `I` | 字符串追加 | `{o:"I", v:" appended text"}` |

**字符串 diff 示例：**
```
原文: "Hello World"
改后: "Hello Beautiful World"

diff-match-patch 的 delta 格式:
"=6\t+Beautiful \t=5"
// 保留6字符("Hello ") + 插入"Beautiful " + 保留5字符("World")

补丁大小: 约 25 字节 (vs 完整字符串 21 字节)
```

**大文件场景(1MB)：**
```
原文: 1,000,000 字符
改了: 中间插入 50 字符

diff delta: "=500000\t+inserted 50 chars here...\t=500000"
补丁大小: 约 80 字节 (vs 完整文件 1MB)

压缩比: 1:12,500 !!!
```

#### ③ Channel (通信通道) — `channel.js` (1045 行)

Channel 是同步的核心引擎，负责：

**上行 (本地→服务器)：**
1. 用户编辑 → Bucket.update() → Channel.update()
2. 取出 ghost → `buildModifyChange(id, newData, ghost)`
3. 计算 diff: `change.buildChange(MODIFY, id, newData, ghost)`
4. 入 LocalQueue → 发送 `c:{ id, ccid, sv, v:{patch} }`

**下行 (服务器→本地)：**
1. 收到 `c:[{change}]` 消息
2. 取出本地 ghost → `applyChange(change, ghost)`
3. 应用补丁: `change.apply(patch, ghost.data)` = 新数据
4. 更新 ghost 版本: `store.put(id, newVersion, newData)`
5. 触发 UI 更新: `emit('update', id, newData)`

**冲突处理 (OT 变换)：**
```
Client A 和 Client B 同时编辑:

A 的本地修改: localPatch
B 的远端补丁: remotePatch (先到达服务器)

1. 先应用 remotePatch → 更新 ghost
2. 计算 transform(localPatch, remotePatch) = rebasedPatch
3. 重新排队 rebasedPatch 发送给服务器
```

#### ④ LocalQueue (本地队列) — `channel.js` 内嵌

**关键策略：合并压缩**
```javascript
// 如果同一个笔记有多个待发送的变更，只发送最新的
LocalQueue.processQueue = function(id) {
  var changes = this.queues[id];
  // 取最后一个变更 (如果有 remove 则优先 remove)
  var sending = changes.reduce((chosen, next) =>
    'remove' === chosen.type ? chosen : next
  );
  // 基于当前 ghost 重新计算 diff
  var change = operation(sending, ghost);
  this.queues[id] = []; // 清空队列
  this.sent[id] = change; // 标记为已发送
  this.emit('send', change); // 发送
};
```

这意味着：**无论用户编辑了多少次，在发送前只会合并为一个补丁**。

#### ⑤ 版本历史 (Revisions) — `channel.js` 末尾

Simperium 的版本历史策略：
```
每个笔记存储:
├── 最近 60 个精确版本 (revisions)     → 每次变更都记录
└── 每 10 个版本一个归档快照 (archive) → 最多 100 个归档

总覆盖范围: 最近 1,060 次变更

示例 (一个有 200 个版本的笔记):
v200, v199, v198, ... v141 (精确版本, 60个)
v131, v121, v111, ... v1   (归档快照, 每隔10个, 14个)
```

### 1.3 Simperium 的已知限制

| 限制 | 值 | 来源 |
|------|-----|------|
| 笔记大小上限 | 无明确限制 (实测约 1-2MB) | 官方帮助文档未提及 |
| 笔记数量上限 | 无明确限制 | 免费无限 |
| 同步频率 | 实时 (WebSocket) | 每次编辑立即发送 diff |
| 存储空间 | 无限 | 完全免费 |
| 精确历史版本 | 60 个 | 源码 `channel.js:1031` |
| 归档历史版本 | 100 个 | 源码 `channel.js:1033-1040` |
| 内容类型 | 纯文本 + Markdown | 不支持附件/图片上传 |
| 加密 | 传输加密 (TLS) | 服务端明文存储 |
| 心跳间隔 | 4 秒 | 源码 `client.js:73` |
| 重连策略 | 3秒 + 每次失败+3秒 | 源码 `client.js:81` |
| 协议 | WebSocket (wss://api.simperium.com) | 自定义二进制协议 |

## 二、1TXT 复用方案

### 2.1 架构映射

```
Simperium 原版                    1TXT (Supabase 替代)
──────────────────────────────    ──────────────────────────────
WebSocket (自定义协议)        →   Supabase Realtime (WebSocket)
Simperium Server              →   Supabase PostgreSQL + Realtime
Ghost Store (内存)            →   localStorage + Supabase 表
Bucket (数据桶)               →   Supabase 表 (note_ghosts)
Channel (通信通道)            →   SupabaseSyncChannel (新写)
Client (WebSocket 客户端)     →   Supabase Client SDK
Auth (认证)                   →   已完成的 OTP 认证

jsondiff (diff 算法)          →   ✅ 100% 复用
diff-match-patch              →   ✅ 100% 复用
change utils (构建/应用/变换)  →   ✅ 100% 复用 (仅改字段名映射)
LocalQueue (本地队列)         →   ✅ 100% 复用 (仅改发送目标)
revisionCache (版本缓存)      →   ✅ 100% 复用
```

### 2.2 关键代码复用清单

| 文件 | 行数 | 复用方式 | 改动量 |
|------|------|----------|--------|
| `jsondiff.js` | 727 | 直接拷贝到 `lib/sync/` | 0 行 |
| `diff_match_patch.js` | 2000+ | 直接拷贝 | 0 行 |
| `util/change.js` | ~200 | 拷贝 + 移除 Simperium 协议封装 | ~20 行 |
| `util/operation.js` | ~80 | 直接拷贝 | 0 行 |
| `ghost/store.js` | 84 | 接口复用，实现替换为 Supabase | 全部重写 |
| `channel.js` LocalQueue | ~100 | 拷贝 + 加入防抖逻辑 | ~30 行 |
| `channel.js` 核心逻辑 | ~300 | 参考重写 (替换传输层) | 全部重写 |

**总结: 约 3000 行代码可直接复用，约 400 行需要重写**

### 2.3 数据流对比

**Simperium 原版流程：**
```
编辑 → Bucket.update() → Channel.buildModifyChange()
     → diff(ghost, newData) → LocalQueue.queue()
     → WebSocket.send("c:{ patch }") → Simperium Server
     → Server.apply(patch) → WebSocket.broadcast() → Other Clients
```

**1TXT 替代流程：**
```
编辑 → VaultMiddleware (5分钟防抖)
     → diff(ghost, newData) → LocalQueue.queue()
     → supabase.from('note_changes').insert({ patch })
     → Supabase Realtime 广播 → Other Devices
     → 本地: apply(ghost, patch) → 更新 UI
```

## 三、资源消耗优化策略

### 3.1 Simperium vs 1TXT 的发送策略对比

| 策略 | Simperium 原版 | 1TXT 优化版 |
|------|---------------|------------|
| 触发时机 | **每次编辑立即发送** | **保持一致: 保存即同步** |
| 发送压缩 | LocalQueue 合并同笔记的多次变更 | ✅ 100% 复用 |
| 空变更检测 | `isEmptyChange()` 跳过 | ✅ 复用 |
| 心跳 | 4秒一次 | 不需要 (Supabase Realtime 自带) |

### 3.2 为什么防抖 + diff 组合是最优解

```
用户连续编辑 1MB 文件 60 分钟:

Simperium 原版 (无防抖, 有 diff):
├── 编辑次数: ~360 次/小时 (假设每 10 秒一个操作)
├── 每次 diff 大小: ~100-500 字节
├── 小时流量: 360 × 300B = 108 KB/小时
├── LocalQueue 合并后实际发送: ~100 次 (有些被合并了)
└── 实际小时流量: ~30 KB/小时

1TXT (与 Simperium 一致, 即时 diff):
├── LocalQueue 自然压缩: 等待 ACK 期间的编辑自动合并
├── 每次 diff 大小: ~100-500 字节
├── 小时流量: ~30 KB/小时 (与 Simperium 一致)
└── 无额外防抖，保存即同步!

对比完整文件上传 (无 diff):
├── 5分钟防抖: 12 次发送/小时
├── 每次上传: 1MB
├── 小时流量: 12 MB/小时
└── 是 diff 方案的 1000 倍!
```

### 3.3 版本历史策略

| 方案 | Simperium | 1TXT (推荐) |
|------|-----------|------------|
| 精确版本 | 60 个 | **30 个** (减少存储) |
| 归档快照 | 每 10 版 1 个, 共 100 个 | **每 10 版 1 个, 共 50 个** |
| 总覆盖 | 1,060 次变更 | **530 次变更** (够用) |
| 压缩策略 | 服务端自动 | 客户端定期合并 + 上传快照 |
| 存储位置 | Simperium 服务器 | Supabase Database (JSON) |

### 4.2 碎片同步 (Diff) — 资源消耗建模

| 用户类型 | 占比 | 人数 | 每日 diff 次数 | 平均 diff 大小 | 日数据量 |
|---------|------|------|---------------|--------------|---------|

### 4.4 压缩策略：防止数据库爆炸

```sql
-- 定期任务: 每月执行一次
-- 1. 对每个笔记，保留最近 30 个 diff，其余删除
-- 2. 同时更新 ghost 快照为最新版

DELETE FROM note_changes
WHERE id NOT IN (
  SELECT id FROM note_changes
  WHERE user_id = target_user_id
  AND note_id = target_note_id
  ORDER BY created_at DESC
  LIMIT 30
);
```

**压缩后 1000 用户数据库大小：**
```
每用户平均 100 篇笔记 × 30 个 diff × 500 字节 = 1.5 MB
1000 用户 × 1.5 MB = 1.5 GB (恒定，不再增长!)
加上 Ghost 快照: 50 MB
总计: 约 1.55 GB ← 远小于 8 GB 额度
```

### 4.5 Pro 套餐极限容量估算

| 瓶颈资源 | Pro 额度 | 单用户月消耗 | 理论上限 |
|---------|---------|------------|---------|
| 数据库 (压缩后) | 8 GB | 1.5 MB | **5,333 用户** |
| 出站流量 | 250 GB | 632 KB | **~400,000 用户** ← 不是瓶颈 |
| Realtime 并发 | 500 | 1 | **500 同时在线** |
| Realtime 消息 | 500 万/月 | 600 条 | **8,333 用户** |
| MAU | 100,000 | 1 | 100,000 用户 |

**实际瓶颈: Realtime 并发连接 (500)**

碎片同步方案下，出站流量几乎可以忽略不计。真正的瓶颈变成了 **Supabase Realtime 的 500 并发连接限制**。

但是！我们可以用 **轮询 (Polling) 替代 Realtime** 来绕过：
```
方案 A: Supabase Realtime (WebSocket)
  ├── 实时推送，延迟 < 1秒
  ├── 受 500 并发限制
  └── 适合: < 500 同时在线

方案 B: 定时轮询 (REST API)
  ├── 每 5 分钟拉取一次新 diff
  ├── 无并发限制 (API 请求无限)
  ├── 延迟 = 轮询间隔 (5分钟)
  └── 适合: > 500 同时在线

方案 C: 混合模式 (推荐)
  ├── 应用前台活跃时: 用 Realtime
  ├── 应用后台/非活跃: 切换为轮询
  ├── 减少 Realtime 并发到活跃用户数
  └── 最优: 500 活跃 + 无限非活跃
```

### 4.6 最终容量估算 (混合模式)

| 套餐 | 月费 | 碎片同步可支持用户 | 整文件同步可支持用户 |
|------|------|-----------------|-------------------|
| **Free** | $0 | ~200 用户 | ~500 用户 |
| **Pro** | $25 | **~5,000 用户** ⭐ | ~2,000 用户 |
| Pro + 超额 | ~$30 | ~8,000 用户 | ~3,000 用户 |

> **碎片同步在 Pro 套餐下可以支持 2.5 倍的用户量！**
> 代价是: 数据库消耗更大 (但有压缩策略控制), 开发复杂度更高

## 五、技术难题与解决方案

### 难题 1: Ghost 一致性
**问题**: Ghost 必须和服务器保持严格一致，否则 diff 计算会出错
**Simperium 方案**: 版本号校验 + 不匹配时回退重新同步
**我们的方案**: 相同策略，版本号不匹配 → 重新拉取 ghost 快照

### 难题 2: 传输层替换
**问题**: Simperium 用自定义 WebSocket 协议 (`0:c:{ json }`)
**方案**: 替换为 Supabase REST (上行) + Realtime (下行)
**复杂度**: 中等 (约 200 行新代码)

### 难题 3: 冲突处理
**问题**: 两台设备同时编辑同一笔记
**Simperium 方案**: 服务端做 OT 变换
**我们的方案**: 客户端做 OT 变换 (复用 `jsondiff.transform_object_diff`)
**风险**: 由于 1TXT 是单用户多设备场景，同时编辑的概率极低

### 难题 4: 首次同步 (新设备)
**问题**: 新设备登录后需要拉取所有笔记
**方案**: 直接拉取 `note_ghosts` 表的最新快照 (完整数据)，无需重放历史 diff
**开销**: 一次性下载 ~1-5MB

### 难题 5: 离线编辑
**问题**: 断网后编辑，恢复后如何同步
**方案**: LocalQueue 缓存所有离线变更，恢复后逐个发送，自动 OT 合并
**Simperium 已解决**: 直接复用其 `resendSentChanges()` 逻辑

### 难题 6: 数据库膨胀
**问题**: diff 补丁持续累积
**方案**: 月度清理任务 + Ghost 快照更新
**影响**: 可控，压缩后 5000 用户仅占 ~1.5GB

## 六、结论

### 选择碎片同步的理由

| 维度 | 碎片 diff | 整文件 | 胜者 |
|------|----------|--------|------|
| 出站流量 | 632 MB/月 | 160 GB/月 | ⭐ diff (253倍) |
| 大文件支持 | 1MB 文件只传 100B | 1MB 文件传 1MB | ⭐ diff |
| 版本历史 | 天然支持完整历史 | 需额外实现 | ⭐ diff |
| 冲突解决 | OT 变换自动合并 | 后写覆盖 | ⭐ diff |
| 代码复用 | 复用 Simperium 3000 行 | 从零写 | ⭐ diff |
| 数据库占用 | 较大 (需压缩) | 极小 | 整文件 |
| 开发周期 | ~8.5 天 | ~2 天 | 整文件 |
| 可靠性 | 需严谨测试 | 简单直接 | 整文件 |

**最终决定: 使用碎片 diff 同步方案**

理由:
1. 出站流量节省 253 倍 → Pro 套餐支持 2.5 倍用户
2. 大文件编辑不再是瓶颈 (1MB 文件只传几百字节)
3. Simperium 的核心算法可直接复用，大幅减少开发量
4. 天然支持版本历史和冲突解决
5. 长期来看是更专业、更可扩展的方案
