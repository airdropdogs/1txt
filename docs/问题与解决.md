# 1TXT 近期问题与解决记录

## 1. 引入 WYSIWYG (所见即所得) 模式遇到的问题

### 问题现象
在使用 `Vditor` 作为 WYSIWYG 模式的编辑器时发现以下问题：
1. **多余的 UI 元素**：在文本前面会出现不需要的 H1/H2 灰色标签。
2. **多余的悬浮框**：出现控制块级元素排版的悬浮删除、上下移动小动作框。
3. **滚动条缺失与尺寸问题**：编辑器内容区域没有滚动条，无法滚动查看长文本，框架并且没有撑满屏幕宽度，导致左右有背景色差。

### 问题原因
1. **类名混淆**：尝试直接通过 CSS 覆盖（如使用 `.vditor-gutters`），但 `Vditor` 内部组件的实际 DOM 结构和类名与直觉并不一致（例如 H1 提示其实是在 `::before` 伪元素中通过 CSS 的 `content` 属性写入的）。
2. **Flex 属性覆盖**：外层容器如 `.note-detail-wrapper` 和 `.note-editor` 在 Flex 布局下，分别设为了 `overflow: hidden` 以及 `flex: 1 0 auto`，这导致编辑器内部容器无法向外传递并挤压伸缩框以支持正常出现内部滚动条。当子元素的尺寸超出父容器计算值时，高度与宽度溢出，无法完美贴合边缘。

### 解决方法

**1. CSS 选择器精确分析**
通过排查并在 Node.js 的模块源代码 `node_modules/vditor/dist/index.js` 及 CSS 中逐个检索结构：
- **悬浮框**：实际通过类名 `.vditor-panel` 控制。
- **H1~H6 标签提示**：并没有独立的标签包裹他们，而是通过匹配 `.vditor-wysiwyg > .vditor-reset > h1::before` 设置 `content: "H1"` 生成的。

**2. 核心 CSS 修补代码写入**
在 `lib/components/wysiwyg-editor/index.tsx` 组件加载中插入自定义样式。

修复多余元素的 CSS：
```css
/* 隐藏浮动块功能栏（悬浮框）*/
.vditor-panel { display: none !important; }

/* 隐藏所见即所得模式中，所有自动展示的标题 H1 ~ H6 伪类字符 */
.vditor-wysiwyg > .vditor-reset > h1::before,
.vditor-wysiwyg > .vditor-reset > h2::before,
.vditor-wysiwyg > .vditor-reset > h3::before,
.vditor-wysiwyg > .vditor-reset > h4::before,
.vditor-wysiwyg > .vditor-reset > h5::before,
.vditor-wysiwyg > .vditor-reset > h6::before,
.vditor-wysiwyg div.vditor-wysiwyg__block::before,
.vditor-wysiwyg div[data-type="link-ref-defs-block"]::before,
.vditor-wysiwyg div[data-type="footnotes-block"]::before,
.vditor-wysiwyg .vditor-toc::before {
  content: none !important;
  display: none !important;
}

/* 隐藏不需要的 Vditor 基础工具栏 */
.vditor-toolbar { display: none !important; }
```

```css
/* 修改 Vditor 原始外框设为占满容器，清除原始限制 */

  border: none !important;
  height: 100% !important;
  display: flex !important;
  flex-direction: column !important;
}

/* Flex 修正：子元素最小高度重置（允许收缩避免撑破父容器）*/

  min-height: 0 !important;
  flex: 1 1 auto !important;
  overflow: hidden !important;
  width: 100% !important;
}
.note-detail-wrapper {
  width: 100% !important;
}

/* 确保内部容器响应 100% 宽度，忽略内联外框限制 */
.note-detail-wrapper .vditor {
  width: 100% !important;
  max-width: 100% !important;
}

/* 重塑中间编辑区的滚动设置 */
.vditor-content {
  flex: 1 1 auto !important;
  overflow: hidden !important;
  display: flex !important;
  min-height: 0 !important;
}
.vditor-wysiwyg {
  height: 100% !important;

  padding: 16px calc((100% - 768px) / 2) !important;
  font-size: 16px !important;
  line-height: 1.7 !important;
  overflow-y: auto !important;
  height: 100% !important;

/* 屏幕较小的时候转为 10% 边距 */
@media only screen and (max-width: 1400px) {
  .vditor-wysiwyg pre.vditor-reset {

  }
}

/* 当应用切换成全宽（Full）模式并且根节点含有 .is-line-length-full 时 */

  padding: 16px 25px !important;
```

**3. 解决冲突样式缓存**
清除过往旧版 `.scss` 文件（例如 `lib/components/wysiwyg-editor/style.scss`）中的设定，防止老旧的静态 padding `16px 48px` 把响应式全屏的内部可编辑框向内挤压导致滚动条不贴边并且留出空白背景。通过以上精确 CSS 样式表注入重写，无缝模拟原版的 Line Length（窄屏/宽屏）模式，实现了滚动条和页面背景全尺寸贴边的原生阅读体验。

通过以上精确 CSS 样式表注入重写，完美解决了从源头带来的视觉污染，既实现滚动能力又完整移除了所有杂项辅助元素。

## 2. Supabase 同步层接入与登出/重登后笔记丢失

### 问题现象
- 用 Supabase + diff-patch 替换原 Simperium 同步后，**首次登录只下来 1 条**笔记；登出再登录 **0 条**。
- 服务器 `note_ghosts` 表实际有 10+ 条数据。
- 新建笔记可以正常 upsert 到服务器，所以"上行"没问题，"下行"挂了。

### 问题原因
1. `SupabaseSyncChannel.start()` 只看本地 `localStorage` 里的 `change_version`（CV）来决定是"全量索引"还是"增量同步"。
2. 登出时虽然清掉了一些 token，但 `1txt_ghost_*` / `1txt_sync_cv_*` 没清。
3. Redux store 在重登时是空的，但 CV 还在 → 走了 `performIncrementalSync(cv)` 分支，结果 `note_changes` 中 `created_at > cv` 的记录数 = 0 → 一条都拉不下来。

### 解决方法
在 `lib/sync/sync-channel.ts` 加 `hydrateFromLocalCache()`：启动时先把本地 ghost 缓存 replay 到 Redux；如果本地一条都没有，**即便 CV 存在**也强制 `performFullIndex()`：
```ts
const localCount = this.hydrateFromLocalCache();
const cv = await this.store.getChangeVersion();
if (!cv || localCount === 0) {
  await this.performFullIndex();
} else {
  await this.performIncrementalSync(cv);
}
```

在 `lib/sync/middleware.ts` 的 `LOGOUT` / `REALLY_LOG_OUT` 里彻底清场：
```ts
for (let i = 0; i < localStorage.length; i++) {
  const k = localStorage.key(i);
  if (k && (k.startsWith('1txt_ghost_') || k.startsWith('1txt_sync_cv_'))) {
    stale.push(k);
  }
}
stale.forEach((k) => localStorage.removeItem(k));
```

附 `docs/diagnose-sync.sql` 的一段诊断 CTE，可以在 Supabase SQL Editor 直接跑，输出每个用户的 ghost / change / cv 三方对照（含 `changes_after_cv` 列），用来快速判断是不是同样的死锁。

## 3. 同步图标在所有笔记标题上都亮起

### 问题现象
左侧栏的同步图标（旋转的小圈）**所有笔记**都显示，而不是只在被同步的那条上。

### 问题原因
`noteHasPendingChanges` selector 还在比对 Redux 里的 note 和老 `state.simperium.ghosts` 里的 ghost：
```ts
!notesAreEqual(state.data.notes.get(id), state.simperium.ghosts[1].get('note')?.get(id)?.data)
```
但我们换 Supabase 后那块 `simperium.ghosts` 永远是空的，比对必然不等 → 全部返回 true。

### 解决方法
1. 在 `lib/state/simperium/reducer.ts` 新增一个 reducer 切片 `pendingChanges: Set<EntityId>`，监听 `SUBMIT_PENDING_CHANGE` / `ACKNOWLEDGE_PENDING_CHANGE`：
```ts
const pendingChanges: A.Reducer<Set<T.EntityId>> = (state = emptySet, action) => {
  switch (action.type) {
    case 'SUBMIT_PENDING_CHANGE': /* add */ ...
    case 'ACKNOWLEDGE_PENDING_CHANGE': /* delete */ ...
  }
};
```
2. selector 改为只读这个 set：
```ts
export const noteHasPendingChanges = (state, noteId) =>
  state.simperium.pendingChanges.has(noteId);
```
3. `lib/sync/middleware.ts` 在 `queueSyncUpdate()` 内首次入队时 dispatch `SUBMIT_PENDING_CHANGE`，timer fire 时 dispatch `ACKNOWLEDGE_PENDING_CHANGE`。

## 4. 同步图标"停手 2 秒才消失"体感太慢

### 问题现象
用户在 Vditor 里输入完，**图标要停留约 2 秒**才消失，让人误以为同步很慢。

### 问题原因
原始策略沿用了 Simperium 的 `BucketQueue`：文本编辑用 2000 ms debounce + 等服务器 `acknowledge` 才清图标。两段串行下来 = 2-3 秒可见。

### 解决方法
**与服务器 ACK 解耦**：图标只反映"用户最近还在改"，停手就清，不等上传完成。失败/离线由 `connectionStatus = 'offline'` 走警告图标的路径感知。

`lib/sync/middleware.ts`：
- 文本编辑 debounce 从 2000 ms → **300 ms**（元数据动作仍是 10 ms）
- timer fire 时立刻 `clearPendingSyncIcon(noteId)` dispatch ACK，然后再异步 `syncChannel.update(noteId, note)`：
```ts
syncTimers[noteId] = setTimeout(() => {
  delete syncTimers[noteId];
  clearPendingSyncIcon(noteId); // ← 视觉立即停止
  if (!syncChannel) return;
  const note = _getState?.()?.data?.notes?.get(noteId);
  if (note) syncChannel.update(noteId, note); // ← 真正上传在后台
}, delay);
```
- `syncChannel.on('acknowledge')` 只保留兜底逻辑，不再重复 dispatch。

效果：停手后约 0.3 秒图标消失，体感"瞬时"。

## 9. 控制台 "Multiple GoTrueClient instances detected" 警告

### 问题原因
- `lib/boot-without-auth.tsx` 用 `createClient()` 起一个 client 处理 OTP 登录。
- `lib/sync/middleware.ts` 又起一个 client 做同步。
- 两个 client 共用同一个 auth storage key (`sb-<project>-auth-token`) → Supabase SDK 警告。

### 解决方法
新增 `lib/sync/supabase-client.ts` 单例：
```ts
let _client: SupabaseClient | null = null;
export const getSupabaseClient = (): SupabaseClient | null => {
  if (_client) return _client;
  const { url, key } = resolveConfig();
  if (!url || !key) return null;
  _client = createClient(url, key);
  return _client;
};
```
`boot-without-auth.tsx` 和 `sync/middleware.ts` 都通过 `getSupabaseClient()` 获取同一个实例。

## 10. 控制台 `[SyncChannel] Skipping corrupted patch:` 反复刷屏

### 问题原因
`SupabaseSyncChannel.getRevisions()` 在还原历史版本时，从空对象 `{}` 起始**正向重放** `note_changes` 里的 patch 序列。但每条 patch 当年是基于"非空 ghost"算的字符串 diff，对 `{}` 调用 `diff_match_patch.diff_fromDelta` 必然抛 `Cannot read properties of undefined (reading 'substring')`。

### 影响
功能上无影响——`getRevisions()` 已 try/catch 跳过坏 patch，最新版本用当前 ghost 兜底始终能拿到。仅日志噪音大。

### 解决方法
`lib/sync/sync-channel.ts` 把 `console.warn` 降为 `console.debug`，并加 `process.env.NODE_ENV !== 'production'` 守卫：
```ts
} catch (e) {
  if (process.env.NODE_ENV !== 'production') {
    console.debug('[SyncChannel] Skipping corrupted patch:', e);
  }
}
```
打包后完全静默。根本性修复（反向重放 / 服务端存历史快照）留待将来若需要修订对比时再做。

## 11. 新用户首条笔记 Markdown 默认关闭

### 问题现象
1TXT 主打 Markdown 体验，但新账号首次"新建笔记"时 Markdown 模式是 **关闭**的，没有 `</> Aa 👁` 三个模式按钮。

### 问题原因
`lib/state/data/middleware.ts` 的 `CREATE_NOTE` 处理用"上一条笔记的 markdown 状态"作为默认；当用户没有任何笔记时 `useMarkdown` 是 `undefined` → falsy → 走非 markdown 分支。

### 解决方法
没有 topNote 时默认 `true`：
```ts
const useMarkdown = topNote
  ? topNote.systemTags.includes('markdown')
  : true;
```
已有笔记时仍按"继承上一条"规则不变。

## 12. CLOSE_WINDOW 在 Sync 未初始化时按钮失灵

### 问题现象
（开发期遇到的小坑）某些场景下 Electron 窗口的关闭按钮没反应。

### 问题原因
`supabaseSyncMiddleware` 早期版本是这样写的：
```ts
if (!syncChannel) return result; // ← 这一行卡住了 CLOSE_WINDOW
switch (action.type) { ... case 'CLOSE_WINDOW': ... }
```
未登录或 sync 还没起来时直接 `return`，CLOSE_WINDOW 永远走不到 dispatch `REALLY_CLOSE_WINDOW`。

### 解决方法
把 `CLOSE_WINDOW` 提到守卫之前，作为"始终处理"的 action：
```ts
if (action.type === 'CLOSE_WINDOW') {
  store.dispatch({ type: 'REALLY_CLOSE_WINDOW' });
  return result;
}
if (!syncChannel) return result;
```
