# 1TXT 版本号与升级机制

> 本文档解释 1TXT 在版本号管理、发版流程、用户升级、数据迁移等方面的全套约定。
> 升级机制采用**最小化设计**：客户端只做"检查→弹窗→跳浏览器下载"，不做自动下载和静默安装。

---

## ⚡ 快速备忘（看这一段就能发版）

```
1. 编辑 version.json（改 version + releaseNotes）
2. npm run release:win
3. 浏览器自动跳到 GitHub New Release 页 → 拖 release/ 里的产物 → Publish
```

完事。3 步，没了。详细解释见 §3。

## 1. 版本号约定（SemVer）

格式 `MAJOR.MINOR.PATCH`，按 [Semantic Versioning 2.0](https://semver.org/lang/zh-CN/)：

| 段位 | 何时 +1 | 1TXT 实例 |
|------|---------|----------|
| **PATCH** | 修 bug、小调整、文案优化 | `1.0.0` → `1.0.1`：修复"同步图标延迟消失" |
| **MINOR** | 新增向后兼容的功能、新设置项、新菜单 | `1.0.1` → `1.1.0`：加文件夹分组、加导出 PDF |
| **MAJOR** | 破坏性变更：数据库 schema 不兼容、必须迁移、配置格式重大改动 | `1.x` → `2.0.0`：把 Supabase schema 拆成多表 |

> ⚠️ **数据迁移是 MAJOR 的硬性触发条件**。任何让老用户的本地 IndexedDB / 远端 Supabase 表结构无法直接读出的改动，必须升 MAJOR 并提供迁移脚本。MAJOR 同时通常会触发**强制升级弹窗**（见 §4.3）。

## 2. 版本号在哪些地方出现（单一事实源原则）

> 只在一个地方维护版本号：**repo 根目录的 `version.json`**。
> 其他位置全部由发版脚本自动同步，不要手工改。

| 位置 | 谁维护 | 怎么变化 |
|------|--------|---------|
| **`version.json`**（repo 根） | **你手工编辑** | 每次发版前改这一份 |
| `package.json` `version` | 自动 | `npm run release` 时同步 |
| `webpack.config.js` getConfig() | 自动 | 从 `package.json` 读 |
| `desktop/config/index.js` | 自动 | 从 `package.json` 读 |
| `desktop/updater/index.js` 比对的当前版本 | 自动 | `app.getVersion()` |
| `electron-builder.json` 产物文件名 | 自动 | `${version}` 占位符 |
| About 对话框 | 自动 | `config.version` |
| Git tag `v1.0.0` | 自动 | 发版脚本打 |

`version.json` 同时是**客户端升级的元数据源**——客户端会拉
`https://raw.githubusercontent.com/airdropdogs/1txt/main/version.json`
来比对。所以**你 push 这个文件 = 用户能感知到新版本**，不需要任何独立服务器。

## 3. 发版流程（2 步，记住这两步就够了）

### 第 1 步：编辑 `version.json`

```json
{
  "version": "1.1.0",
  "downloadPageUrl": "https://github.com/airdropdogs/1txt/releases/latest",
  "webAppUrl": "https://1txt.pkpkpk.com",
  "releaseNotes": "新增文件夹分组、离线模式开关。修复同步图标延迟。",
  "minSupportedVersion": "1.0.0",
  "force": false
}
```

通常只用改 `version` 和 `releaseNotes` 两个字段。`releaseNotes` 是给用户在升级弹窗里看的简短文案（1-3 行就够），详细 changelog 写在 `RELEASE-NOTES.md`（可选，给打开 GitHub 的人看）。

### 第 2 步：执行一个命令

```powershell
# 同时打 Windows 包（推荐）
npm run release:win

# 不打包，只发版本号（macOS / Linux 包用 GitHub Actions 时用）
npm run release
```

脚本会**自动完成**：

1. 校验 `version.json` 版本号合法且 > 当前
2. 校验工作区干净
3. 把 `version.json.version` 同步到 `package.json`
4. （`:win` 时）`npm run build:win` 产出 NSIS + ZIP
5. `git add` + `git commit -m "chore: release v1.1.0"`
6. `git tag v1.1.0`
7. `git push --follow-tags`
8. 自动打开 `release/` 文件夹 + 浏览器到 GitHub New Release 页

### 第 2.5 步（手工，1 分钟）

浏览器已经为你打开 GitHub New Release 页，把 `release/` 文件夹里的产物**拖进去**，点 Publish 就完事。

> 这一步可以跳过：客户端的升级提示**只看 `version.json`**，不读 GitHub Release。
> 但是用户点"去下载"会跳到 `https://github.com/airdropdogs/1txt/releases/latest`——所以最好还是把产物挂上去，否则用户跳过去看不到新版本下载。

### 任何一步出错怎么办？

脚本会立刻 abort，本地不会留下半成品。修复后重跑即可。最常见的两种错：

- "version.json.version (1.0.0) 与 package.json 一致" → 你忘了改 version.json 的版本号
- "工作区还有未提交修改" → 先 `git commit` 那些杂事再发版

## 4. 升级机制（用户视角）

### 4.1 整体设计

| 项 | 选择 |
|----|------|
| 自动下载 | ❌ 不做 |
| 静默安装 | ❌ 不做 |
| 弹窗 | ✅ 弹一个对话框 |
| 跳转 | ✅ 点"去下载"用系统浏览器打开下载页 |
| 跳过 | ✅ 用户可以"跳过此版本"，下次启动不再骚扰 |
| 强制升级 | ✅ 预埋，紧急情况启用，不可跳过 |

NSIS 安装版与 ZIP 解压版 **走同样逻辑**，没有任何差异。下载页让用户自己选要装哪种。

### 4.2 普通升级提示

启动 5 秒后，主进程异步拉取 `version.json`，若：

- `version.json.version` > 当前 `app.getVersion()`，且
- 用户没有"跳过"过这个版本号

就弹这个对话框：

```
┌──────────────────────────────────────┐
│  发现新版本                          │
│                                      │
│  1TXT 1.1.0 已发布                   │
│                                      │
│  当前版本：1.0.0                     │
│  最新版本：1.1.0                     │
│                                      │
│  新增文件夹分组与离线模式...         │
│                                      │
│  点击"去下载"将在浏览器中打开下载页。│
│                                      │
│   [去下载]  [跳过此版本]  [稍后提醒] │
└──────────────────────────────────────┘
```

| 按钮 | 行为 |
|------|------|
| 去下载 | `shell.openExternal(downloadPageUrl)` 跳浏览器，对话框关闭 |
| 跳过此版本 | 把 `1.1.0` 写入 `userData/skipped-versions.json`，**下次启动不再为此版本提示**，但 `1.2.0` 来了照常提示 |
| 稍后提醒 | 什么都不做，下次启动再问 |

也可以从主菜单 **Help → Check for Updates…** 手动触发；手动触发时若已是最新版本会显示"已是最新版本"，失败也会显示错误提示。

### 4.3 强制升级（预埋）

`version.json` 中两个字段任一命中，就改弹强制升级对话框：

| 字段 | 含义 |
|------|------|
| `force: true` | 全员强制 |
| `minSupportedVersion: "1.5.0"` | 当前版本 < 1.5.0 的用户强制 |

强制升级对话框：

```
┌──────────────────────────────────────┐
│  ⚠ 需要升级                           │
│                                      │
│  当前版本已不再支持，请立即升级      │
│                                      │
│  当前版本：1.0.0                     │
│  最新版本：2.0.0                     │
│                                      │
│  由于同步协议或数据格式发生重大变更，│
│  旧版本无法继续使用。                │
│                                      │
│  请选择升级方式：                    │
│                                      │
│   [升级桌面版]  [使用 Web 端]  [退出]│
└──────────────────────────────────────┘
```

| 按钮 | 行为 |
|------|------|
| 升级桌面版 | 跳浏览器到下载页，**关闭应用** |
| 使用 Web 端 | 跳浏览器到 `webAppUrl`，**关闭应用** |
| 退出 | 直接关闭应用 |

强制升级**不能跳过**，无法关闭对话框，只能选其中一项。

### 4.4 所有客户端配置（一行也不用改）

```json
// desktop/config-updater.json
{
  "updater": {
    "metadataUrl": "http://1txt.pkpkpk.com/version.json",
    "downloadPageUrl": "http://1txt.pkpkpk.com/down",
    "webAppUrl": "http://1txt.pkpkpk.com",
    "delay": 5000
  }
}
```

> 不挂服务器也行：把 `metadataUrl` 留空字符串 `""`，updater 直接跳过检查、不报错。

## 5. 数据迁移策略

### 5.1 PATCH（1.0.0 → 1.0.1）
零风险，IndexedDB / Supabase schema 不变，直接覆盖安装即可。

### 5.2 MINOR（1.0.0 → 1.1.0）
向后兼容：
- 新增字段先在 schema 里加（NULLABLE），客户端读时兼容缺失
- 新功能默认关闭，让老用户主动开
- 不删除任何字段、不改名

### 5.3 MAJOR（1.x → 2.0.0）

破坏性变更必须做的事：

1. **写迁移脚本** `docs/migrations/v1-to-v2.sql`，让用户在 Supabase Dashboard SQL Editor 执行
2. **本地 IndexedDB 升级** 在 `lib/state/persistence.ts` 监听 `onupgradeneeded`，老数据按需转换
3. **`version.json` 配置**
   ```json
   {
     "version": "2.0.0",
     "minSupportedVersion": "2.0.0",
     "force": true,
     "releaseNotes": "重大版本升级，需要执行数据库迁移脚本，详见下载页说明。"
   }
   ```
   旧客户端启动→直接弹强制升级对话框。
4. **下载页提供完整迁移指引**，包括：备份建议、SQL 执行步骤、回滚方案。

## 7. 常见问题

### 7.1 用户卸载后数据会丢吗？
- **NSIS 安装版**：`electron-builder.json` 已设 `deleteAppDataOnUninstall: false`，卸载不删 `%APPDATA%/1TXT`
- **ZIP 解压版**：数据在 EXE 同级 `1txt-data/`，删整个解压目录才会丢
- 即使本地数据丢了，重新登录从 Supabase 拉回来即可

### 7.2 ZIP 解压版用户怎么升级？
没有自动覆盖。流程：
1. 弹窗 → 用户点"去下载" → 浏览器打开下载页 → 下载新版 ZIP
2. 解压到一个新目录
3. **把老目录里的 `1txt-data/` 整个剪贴到新目录**（数据/设置/登录态都在这里面）
4. 删旧目录、用新目录里的 EXE 启动

下载页一定要写明这个步骤。

### 7.3 NSIS 安装版用户怎么升级？
1. 弹窗 → 用户点"去下载" → 浏览器打开下载页 → 下载新版 Setup.exe
2. 双击运行，覆盖安装（NSIS 会保留 `%APPDATA%/1TXT` 数据）

### 7.4 想停止某个老版本继续登录怎么办？
不修客户端代码，只改 `version.json` 即可：

```json
{
  "version": "1.5.0",
  "minSupportedVersion": "1.2.0",
  "force": false
}
```

所有 < 1.2.0 的用户启动后会被强制升级，>= 1.2.0 的用户照常使用。

### 7.5 我什么都没部署，客户端会报错吗？
不会。`metadataUrl` 请求失败会被静默吞掉（只在日志里 info 一行），不影响主流程。手动菜单触发时才会显示"无法连接到更新服务器"。

### 7.6 想完全关掉升级检查？
把 `desktop/config-updater.json` 的 `metadataUrl` 改成 `""` 即可。

## 8. 服务器 / 域名相关

### 8.1 你**不需要**任何服务器
- 升级元数据：`https://raw.githubusercontent.com/airdropdogs/1txt/main/version.json`（GitHub raw，免费免维护）
- 安装包下载：`https://github.com/airdropdogs/1txt/releases/latest`（GitHub Release，免费免流量费）

只要 GitHub 不挂、能 push，发版就能完成。

### 8.2 GitHub raw 缓存
GitHub raw 链接有 ~5 分钟 CDN 缓存。意味着 `git push` 后 5-10 分钟内全球用户才能逐步看到新版本通知。这是可以接受的——升级不是即时通信。

### 8.3 关于 `1txt.pkpkpk.com`（可选）
如果未来你有这个域名：
- Web 端：部署到这个域名（详见 `Web端实现.md`）
- 想自托管 version.json：把 `desktop/config-updater.json` 的 `metadataUrl` 改成 `https://1txt.pkpkpk.com/version.json` 并按格式上传即可，**客户端代码无需任何改动**。
- `webAppUrl` 字段：强制升级时弹"使用 Web 端"按钮会跳到这里，建议保留指向你的 Web 端。
